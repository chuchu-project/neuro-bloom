# 端到端延迟怎么测、测出来是多少

这份文档对应「5 件事」里的第 5 件。目标不是把数字写得好看，而是能当着评委的面**现场跑一遍**，出来的数还能解释清楚。

## 一、先说清楚「延迟」到底是哪一段

从脑子里产生一个波，到屏幕上画面变化，中间有四段：

| 段 | 是什么 | 大概多久 | 能不能改 |
|---|---|---|---|
| A 采集 | 电极 → 板子 → USB/WiFi → 电脑 | 毫秒级～几十毫秒 | 板子决定的 |
| B 攒窗口 | 要凑满 4 秒数据才做一次频谱分析 | **4000 ms** | 能改，但要重新标定判定阈值 |
| C 计算 | Welch 算频带 → α/β → 判定 → 策略层 → 世界四键 | **< 1 ms** | 已经很快 |
| D 传输 | 桥接广播 → 浏览器 / Unity 收到 | **1～3 ms** | 本地环回，基本是固定成本 |

所以「端到端 ≈ 4 秒」里，**99.9% 是 B 段**，不是代码慢。这一点必须主动讲清楚，否则评委看到 4 秒会以为系统卡。

## 三、已经测到的数（2026-10-24，本机，演示样本，正式步长 2 秒）

```
样本：9 条带时间戳的消息（共收到 10 条，已跳过接入瞬间的 1 条缓存快照）
消息间隔：2.0 秒一条

1) 攒窗口     4000.0 ms
2) 分析计算   1.0 ms
3) 传输排队   2.3 ms  （95 分位 3.7 ms，最慢 4.1 ms）

端到端（1+2+3）中位：4003.3 ms
```

**正式演示就是步长 2 秒**，也就是每 2 秒更新一次画面。所以：

- 从「数据凑齐」到「控制台收到」：**3.3 毫秒**（分析 1.0 + 传输 2.3）
- 从「这一刻的脑电」到「画面反映它」：**4 秒窗口 + 最多 2 秒等待 = 最坏 6 秒**

## 四、答辩时怎么讲（照念就行）

> 我们的判定每 4 秒做一次，因为要凑够一个完整的频谱窗口，这是脑电分析本身的要求。窗口一满，从算完到控制台收到只要 3 毫秒左右（分析 1.0、传输 2.3），瓶颈完全不在软件。如果要更快，就要把窗口缩到 2 秒，代价是频率分辨率变粗、判定更容易抖，我们权衡后选了 4 秒。

不要写「延迟低于 100ms」，那是假的，会被追问。

## 五、这些数是从哪来的

`tools/latency_probe.py` 读两个字段，字段由 `eeg_service/main.py` 在发消息前打上：

- `t_win_end`：这个 4 秒窗口最后一个样点到手的时刻（墙钟时间）
- `t_analysis_ms`：从这一刻到算完、策略层跑完花了多少毫秒
- `win_seconds`：窗口长度

脚本用「收到消息的时刻 − t_win_end」得到传输+排队，再加上窗口和分析时间。缺字段的老服务，脚本会直接说「服务端没打时间戳」，不会拿 0 硬算。
